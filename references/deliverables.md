# 交付标准

## 统一需求包

默认完整任务应有以下产物，具体文件名和格式可按项目调整，但角色与引用稳定：

| 产物角色 | 必须解决的问题 |
|---|---|
| prd | 项目范围、事实/假设、功能地图、角色、页面、规则、状态、生效/历史边界、非功能协议、依赖和交付关口 |
| api | 本期逐端点机器可校验契约：方法、路径、参数、请求、响应、鉴权、错误、版本、幂等及异步/回调；采用OpenAPI JSON优先 |
| dictionary | 字段ID、类型、单位、默认、必填/条件必填、枚举、边界、清空语义、错误、读写权限；可由API派生但含业务约束 |
| prototype | 本期页面线框、字段分组、操作入口，以及正常、加载、空态、校验失败、冲突、无权限等适用状态；区分线框与真实实现 |
| trace | 独立需求ID→页面/动作→字段/接口→角色→验收ID→阶段/状态；API每个operationId必须可追踪 |
| fixtures | 独立选定输入和唯一预期输出，覆盖正常、边界、重复、并发、部分完成与失败恢复；不是用计算结果反填预期 |
| review | 审查发现、证据、关闭条件、实际修订位置、复核结果与尚未解决项；没有发现也说明审查范围，不虚构问题数 |
| verification | 实际执行的校验命令/范围/结果/未覆盖内容；不把文档结构通过称作软件UAT通过 |
| readme | 统一阅读顺序、文件关系、版本、运行校验方式与范围边界 |

补 `requirements-manifest.json` 绑定文件角色，见bundle-manifest.md；交付压缩包与哈希清单。用户明确只要某一产物时，可在manifest记录scope=partial并如实列明未含内容，不能以部分包宣称全套完成。

## 每个模块的实际颗粒度

用唯一ID定位需求，不只用“商品管理”“商店设置”等大模块名。

1. 入口与页面：路由/入口、布局分组、来源、列表列、筛选/排序/分页、详情、表单和操作区。
2. 字段：显示名与契约键映射、类型、长度/精度/单位、默认、可空/可清、必填时机、枚举及其维护入口、依赖变更行为。动态schema须提供版本、来源和不支持值的处理。
3. 动作：谁能在什么状态点击；确认内容；服务端重验；本地原子效果；外部效果；成功页面；错误及重试；审计和通知。
4. 状态：完整转换表，而不是状态名称列表。当前状态＋事件＋守卫＋数据变化＋下一状态＋重复/乱序/失败的行为。
5. 权限：角色×动作×敏感字段×对象范围。允许名单、拒绝策略、再次验证、导出与下载重验；不能只隐藏按钮。
6. 生效：保存草稿、发布、回滚、实时数据、既有会话/报价/订单/通知的版本绑定；不能“恢复旧内容”顺便倒退真实库存或交易。
7. 验收：固定条件、数据、步骤、唯一状态/金额/错误/页面结果、证据。不要只写“结果正确”。

## 接口最低标准

- 全部本期页面动作有实际端点或明确纯本地行为；无`GET/POST`、`approve|reject`等简写充当真实端点。
- 请求与响应分别定义；禁止一个自由JSON对象覆盖整个模块。字段条件若不便用schema表达，写明确服务端条件及错误码，并给正反例。
- 明确未知字段、null、空字符串、省略、空数组、清空的区别；同一字段不能在PRD与schema使用不同单位/名字。
- 每个端点有唯一operationId、阶段、关联需求/验收、角色或能力鉴权。实体ID不等于凭证。
- 响应字段按权限剔除时，schema不能又要求无权限用户必须返回该秘密字段；必要时分别定义视图。
- 对外部供应商明确自有边界契约与真实原生适配依赖；未选供应商不得编造已完成能力。

## 需求与实现的区分

需求文档不必装入所有DDL和应用代码。独立原型、接口、数据字典与部署协议可以是附件，但必须真实存在、版本绑定且能供下游使用。最终视觉、真实渠道适配、生产数据和软件测试尚未发生时，必须准确陈述其状态。

不要让AI生成的模块数、端点数、文档页数或简单regex校验变成质量指标。评审的核心是：产品、开发、测试用同一输入推演时能否得到同一答案。
