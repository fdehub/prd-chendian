# 执行步骤与完成门槛

适用于要求“完整需求包”的任务。用户明确只要局部审查/指定文档时按其范围执行并如实标注，不能反过来替用户扩大任务。下面是工作约束，不固定业务功能数量。

## 先建三张表

在正式正文前建立并维护：

1. 范围表：需求ID、模块、角色、阶段、本期/后续/排除、来源（用户要求/观察/提案）、状态。
2. 决策表：决策ID、未知项、临时假设或空值、负责角色、影响需求、阻断关口、未提供时行为、批准状态。不编造实际人员。
3. 产物表：统一入口和每个附件路径、版本、权威数据来源。用户举一个模块的缺陷，范围表中的其他模块仍必须完成。

## 按同一模板展开每个本期功能

缺一项就记为未完成或明确“不适用及理由”，不能把标题留着当完成。

```text
需求ID / 名称 / 阶段 / 来源 / 提案或批准状态
目标角色与入口：谁，从哪里进入，完成什么。
页面：路由、区块顺序、数据来源、列表列、筛选/排序/分页、详情与表单。
字段表：字段ID、界面名、契约键、控件、类型、单位/精度、默认、
        必填/条件、范围/枚举、清空/省略/null、错误码和字段权限。
动作表：动作ID、按钮/触发、权限与对象范围、当前状态、守卫、确认内容、
        服务端校验、本地原子效果、外部效果、成功状态/界面、
        明确失败/未知/重复/并发/重试的行为、审计及通知。
生效/历史：保存/发布/回滚是否存在，哪些旧记录或异步任务沿用快照。
契约：具体operationId和schema；纯本地动作也要说明，不虚构API。
验收：case ID，固定Given/When和结构化Then，包含正反例与适用边界。
```

只有字段名清单不合格；只有状态名称不合格；只有“保存成功”不合格；仅列接口路径不合格。

## 计算与状态要求

- 计算必须定义输入单位、顺序、精度、舍入、边界、空值和错误，给固定输入及唯一数值预期。至少有一个边界反例；不能直接使用函数计算结果生成expected。
- 状态表每行写当前状态、事件、守卫、原子动作、下一状态、重复/乱序/未知的处理。操作失败后必须能解释资源是否仍被占用。
- 幂等必须区分请求键去重、业务事件唯一与并发互斥，不能写“有幂等键所以不会重复”。
- 需要外部渠道时明确自己掌握的状态和待验证的外部结果；不知道不等于失败，不凭返回URL断定真实成功。

## 原型与接口要求

- 本期每个主要页面有线框；字段和动作可以映射到正文，不接受只有首页效果图。
- 正常/加载/空态/校验失败/版本冲突/无权限按适用性提供。不能用同一“出错了”覆盖所有错误。
- API操作有独立ID、鉴权、完整参数/请求/响应schema、错误、版本/幂等条件；写明条件必填。不同视图权限与schema必填不得冲突。
- 生成器、数据字典和原型只能共享已定义的规则。禁止用自由JSON对象、假端点或全部返回200填满目录。
- `requirements-manifest.json`内提供`requirements`及`acceptanceCases`，结构见bundle-manifest。每本期需求至少一条可判定用例；每实际端点至少被一个需求引用。纯本地动作使用`localOnly: true`并给理由。

## 完成前必须做

1. 按review-gates推演关键链路，找出规则冲突和缺项，记录发现位置与复现数据。
2. 修正文和全部关联附件；附修复定位，不仅叠加优先级说明。
3. 运行项目自己的参考算例/语义检查，再运行结构校验；对实际执行的每项保留结果和覆盖边界。
4. 检查统一入口链接、产物角色、版本、字段名、角色名、错误码、单位、状态和用例一致。
5. 执行交付门槛：完整任务缺附件/需求无用例/API无追踪/校验失败/关键规则仍多解，不能称完成。真实业务输入尚缺时明确是生产门禁还是设计阻断。

最终答复给统一文档和整包链接，说明实际完成与实际验证。不要宣称绝无争议、已获得用户批准、已完成生产接入。

## skill分享门槛

分享skill的包与用户的需求交付包是两种东西：前者只含通用指令、独立虚构示例和通用工具；后者才含用户业务资料。不要把两者套娃打包。分享前列出全部文件，检查内容及嵌套归档；样例必须有synthetic声明和可核实的生成来源说明，不能只把客户名称替换掉。
