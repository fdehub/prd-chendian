# 审查与修复门槛

## 审查顺序

先检查跨模块规则，再检查模块内部细节；不要只看目录是否齐全。

| 审查面 | 要主动推演的失败 |
|---|---|
| 业务闭环 | 正常、取消、撤销、部分完成、失败、结果未知、人工纠错后，金额/数量/权限/状态是否仍能对账 |
| 并发和重放 | 不同幂等键、不同窗口、延迟/重复/乱序回调、超时后重试；幂等键是否被错误当作业务锁 |
| 计算 | 精度、舍入、分摊尾差、基数、顺序、0值、上限、多币种/单位；不能把未选供应商当另一算法的任意出口 |
| 初始化 | 空库能否仅通过正常入口完成配置？“已发布”“可售”“已连接”“开放”是否互相等待 |
| 引用完整性 | 被引用的配置、维护入口、通知、人员角色、模板和参数是否实际有规格；未知值与未设计功能是否被混淆 |
| 生效与历史 | 保存/发布/回滚、旧报价/会话/记录、异步任务、缓存和已发生真实事件的边界 |
| 安全与身份 | ID是否被当凭证；注册/找回/MFA/首管理员/恢复/换邮箱/撤权是否闭合；限频和期限是否可判定 |
| 契约一致性 | 名称、类型、单位、默认、清空、角色、错误、状态在PRD/原型/API/字典/测试之间是否同义 |
| 可验收性 | 同一条件是否留了“或”双答案；测试环境/数据集/负载/阈值/统计是否固定；是否只给场景名没有预期 |
| 范围与责任 | 本期/后续/排除一致；谁给输入、谁做适配、何时阻断、什么属于变更、交付哪些证据 |

## 记录与修复

发现项应有：稳定ID、严重度、原文位置、可复现输入、两种解释或断点、实际影响、关闭条件。严重度按是否阻断当前交付判断，不为凑数量夸大。

用户要求审查时，先给真实结论，不必擅改其经营决定。用户要求修复时：

1. 直接修正文和相关附件，消除旧冲突，不只增加一个“新规则优先”附录。
2. 技术/产品默认方案可明确提出并实现为待评审规格；真实经营参数和外部能力仍列入决策/依赖台账。
3. 为修复添加独立预期的正反例和跨模块场景，运行适用校验；若用参考状态模型，明确它并非真实数据库并发测试。
4. 更新修复表：原发现→规则ID→变更→证据→剩余关口。不要以“写了一个段落”自动标独立评审通过。
5. 对新规则再做一次跨模块推演，防止修取消库存时破坏发货，或修退款时破坏退货数量。

## 交付状态的用词

- **草案/待评审**：产品方案尚未由用户确认。
- **规格已修订、内部校验通过**：能说明修了什么、校验实际覆盖什么。
- **用户已批准基线**：必须有真实批准记录，不能替用户签字。
- **实现测试通过/可上线**：必须有相应软件与环境证据；文档脚本通过不能支持此结论。

尚有关键歧义时明确不通过实施基线评审，指出阻断项。不能一边说“全部修复”，一边把缺失接口/页面/状态统称“上线前填值”。
